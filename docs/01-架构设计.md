# 01 · 架构设计

## 1. 分层与职责

```
┌───────────────────────────────────────────────────────────┐
│ 表现层  app.py（Streamlit）                                 │
│   对话渲染 / 参数调试 / 知识库上传与重建 / 服务卡片跳转        │
├───────────────────────────────────────────────────────────┤
│ 编排层  src/graph.py（LangGraph）                           │
│   意图路由 · 槽位检查 · 条件分支 · 多轮记忆 · 统一收口         │
├───────────────────────────────────────────────────────────┤
│ 能力层                                                     │
│   knowledge.py  检索（Chroma）                              │
│   recommender.py 服务推荐（语义 + 规则）                     │
│   prompts.py    提示词 / 离线抽取式摘要                      │
├───────────────────────────────────────────────────────────┤
│ 基础设施层                                                  │
│   llm.py       模型客户端（通义 / 豆包 / 离线）               │
│   embedding.py 向量化（本地哈希 / 云端）                     │
│   config.py    配置与环境变量                                │
└───────────────────────────────────────────────────────────┘
```

**约束**：编排层不直接碰 Chroma 或 HTTP，只调能力层；能力层不感知 Streamlit。这样 `scripts/chat_cli.py` 能复用同一套逻辑，测试无需启动 UI。

## 2. 为什么用 LangGraph 而不是「一个大 Prompt」

初学者常见做法是把意图识别、知识检索、推荐全塞进一个 prompt，让模型一次输出。问题有三个：

1. **不可控**：模型可能该追问时直接编答案，该推荐时答非所问
2. **不可调试**：出错时不知道是检索没召回、还是模型没用资料
3. **不可扩展**：加一个分支就得改整段 prompt，回归测试全靠肉眼

LangGraph 的做法是把流程拆成节点，用条件边决定走向：

```
analyze ──┬─(信息不足)──▶ ask_more ────────────────┐
          ├─(知识类)───▶ retrieve ─▶ generate ─▶ recommend ─┤
          ├─(服务类)─────────────────────────▶ recommend ─┤
          └─(闲聊)────▶ chitchat ───────────────────────┤
                                                     finish ─▶ END
```

好处：每一步的输入输出都能在界面上看到（「工作流执行轨迹」），面试演示时可以直接指着说"这一步是检索，这一步是生成"。

## 3. RAG 链路的关键细节

### 3.1 切分策略

不做无脑定长切分，而是**两级切分**：

1. 先按 `##` 二级标题切章节 —— 养护知识天然按「症状 / 原因 / 处理」分节，按标题切保证语义完整
2. 章节内再用 `RecursiveCharacterTextSplitter`（380 字 / 重叠 60）按中文标点兜底

`chunk_size=380` 是权衡结果：太小会丢上下文（"禁食 4-6 小时"丢失主语），太大则一条命中带回大量无关内容，稀释 prompt。

### 3.2 提升召回的三个小技巧

| 技巧 | 做法 | 效果 |
| --- | --- | --- |
| 标题拼进正文 | `embed_text = 章节标题 + "\n" + 正文` | 用户问「疫苗」时，标题里的关键词也能命中，不依赖正文重复出现 |
| 短碎片过滤 | 少于 20 字的 chunk 丢弃 | 避免"注意事项："这种无信息碎片占用 top_k |
| 相似度阈值 | `score < 0.12` 判为未覆盖（该分数是混合分，不是纯余弦） | 宁可说"不知道"，也不让模型拿弱相关片段硬编 |

### 3.3 召回 + 重排：把"所有文档都是 0.067"救回来

这是项目里真实踩过的坑，也是最能讲的一段。

**第一版**：直接用哈希向量的余弦值排序，阈值 0.18。结果 5 个测试问题全部触发"知识库未覆盖"兜底——所有片段的分数都挤在 0.06-0.14 之间，几乎没有区分度。

**诊断**：把 top5 的分数打出来看，发现相关片段的余弦也只有 0.08。原因是余弦对长度敏感：一个 200 字的片段里只有 2-3 个词和问题重合，分母（片段向量模长）却全算进去了。

**第二版**：加一层词项覆盖率重排，`score = 0.65 × 覆盖率 + 0.35 × 余弦`。仍然不行——覆盖率所有文档都等于 0.067。

**再诊断**：根因是**中文词边界被切碎了**。查询切成 2-gram 得到"克猫","猫粮","布偶"等 15 个片段，而文档里写的是"克干粮"，"克猫粮"和"克干粮"共享的只有单字"克"，一个 bigram 都对不上。

**最终方案**：

1. **去标点 + 去停用字 + 2-gram**：`的/了/是/吗` 组合出来的 bigram 没有区分度，先剔除
2. **IDF 加权**：`覆盖率 = 命中词项的 IDF 之和 / 查询词项总 IDF`。让"布偶""拉稀"这类罕见词主导，压住"猫""喂"这类高频字
3. **品种词不参与主题打分**：`狗/猫/狗狗` 只用于过滤，否则「狗狗拉稀」会被《剪指甲与足部护理》顶到第一（实测就是这样）
4. **先召回后重排**：Chroma 召回 4 倍候选，再用混合分重排取 top_k

修复后同一批问题的分数：

| 问题 | 修复前 top1 | 修复后 top1 | 区分度 |
| --- | --- | --- | --- |
| 三个月大的布偶猫喂多少克猫粮 | 0.073（成猫喂食量） | **0.150**（幼猫每日喂食量参考） | top2 仅 0.030 |
| 狗狗拉稀两天要紧吗 | 0.128（呕吐） | **0.383**（腹泻与软便） | top2 仅 0.154 |
| 猫呕吐要禁食多久 | — | **0.431**（呕吐：先分清类型） | top2 仅 0.163 |

这段经历说明一个道理：**RAG 的效果瓶颈往往不在模型，而在检索**。而检索出问题时，要有"打日志看分数构成"的习惯，而不是凭感觉调阈值。

### 3.4 为什么默认用本地哈希向量

`all-MiniLM-L6-v2` 需要从 HuggingFace 下载 80MB，国内新手第一步就会失败。本地实现用字符 2-gram/3-gram + 签名哈希，纯标准库、零下载，对「关键词高度重合」的垂直领域检索够用。

代价是**没有语义泛化**：「拉稀」和「腹泻」不算近义。所以知识库里两种说法都会写进去（这也是内容侧的工程手段）。需要更强语义时，把 `EMBEDDING_PROVIDER` 切到 `dashscope` 即可，代码里已做维度变化检测与自动重建。

## 4. 幻觉控制（四道闸）

1. **prompt 约束**：只依据参考资料作答、禁止编造药名剂量、不确定就明说
2. **检索兜底**：相似度不足直接返回"资料里没有"，不进模型
3. **模型兜底**：模型调用异常时降级为抽取式摘要，页面不白屏
4. **引用可见**：每条回答下方可展开「参考资料」，用户能核对依据

另外，涉及用药剂量一律不给具体数字，只说"需由兽医按体重开具"——这是垂直领域 Agent 必须守的边界。

## 5. 多轮记忆

- `MemorySaver` + `thread_id`：同一会话共享 state，切换会话换 `thread_id`
- `history` 只保留最近 6 轮（12 条消息），控制 token 成本
- 画像（品种/年龄/症状）**跨轮累积**：第一轮说"我家是布偶猫"，第三轮问"它吐了"时仍知道是猫，从而给猫-specific 建议

这是"槽位检查"能工作的前提：`analyze` 每轮把新信息 merge 进 `profile`，缺什么补问什么。

## 6. 服务推荐的融合打分

```
final = 0.5 * 语义相似度(归一化) + 0.5 * 规则命中分
规则命中分 = min(1, 关键词命中数 × 0.5 + 场景标签命中数 × 0.3)
```

为什么不用纯向量：纯向量会把「猫洗澡」推成「猫咪喂养」（都在"猫+清洁"语义空间里），业务上不可接受。
为什么不用纯规则：用户说「毛孩子没人管了」，规则命中不了任何关键词，但语义上明显指向"上门喂养"。

**双重过滤**：`status != 1`（已下架）直接跳过，`pet_type` 不匹配直接跳过。这两条让推荐结果与平台数据保持一致，不会推荐用户点进去发现下架的服务。

## 7. 成本与性能

| 手段 | 说明 |
| --- | --- |
| 意图识别走规则 | 不消耗 token，延迟 <1ms |
| 服务向量预计算 | 启动时算一次，推荐时只算 query 向量 |
| 知识库持久化 | 建一次落盘，后续直接加载，不重复 embedding |
| history 裁剪 | 只带最近 4 条进 prompt，控制上下文长度 |
| 流式/非流式 | 当前非流式，便于展示完整结构；接流式只需改 `generate` 一处 |

## 8. 已知边界与演进

| 现状 | 生产做法 |
| --- | --- |
| MemorySaver 进程内存储 | 换 Redis / Postgres checkpointer |
| 无 query 改写 | 加一步「指代消解 + 查询改写」节点（「它」→「布偶猫」） |
| 无 rerank | 检索 top20 后用 bge-reranker 精排 top5 |
| 无评估集 | 建 30-50 条问答对，评估召回率与 answer faithfulness |
| 单机 Streamlit | 换 FastAPI + 前端，或加 langserve |
| 无用户反馈闭环 | 加 👍/👎，落库后做 badcase 分析 |
