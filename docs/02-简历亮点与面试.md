# 02 · 简历写法与面试讲解

## 一、简历项目描述（可直接用）

> **宠物养护智能咨询 Agent** ｜ 个人项目 ｜ Python / LangChain / LangGraph / Chroma / Streamlit
>
> 面向宠物养护垂直领域的 RAG 智能体，与自研「宠物服务上门平台」打通，实现"咨询—诊断—服务转化"闭环。
>
> - 用 **LangGraph 条件路由**替代单体 Prompt：意图识别、槽位检查、知识问答、服务推荐拆为独立节点，配合 `MemorySaver` 实现跨轮记忆，意图可解释、链路可调试
> - 构建 **6 篇垂直知识库**（按二级标题两级切分 + 标题入向量），检索加相似度阈值兜底，配合 4 条 prompt 约束与引用展示，显著降低幻觉
> - 设计**双模式降级**：有 API Key 走 DeepSeek / 通义 / 豆包（OpenAI 兼容协议，一套客户端切三家），无 Key 自动降级为抽取式摘要，保证任何环境都能完整演示
> - 服务推荐用**语义相似度 + 关键词规则融合打分**，过滤已下架服务与不匹配品种，推荐卡片直连平台预约页，打通咨询到下单
> - Streamlit 端支持知识库上传/重建、`top_k`/阈值/温度实时调试，并可视化每一步工作流轨迹

## 二、五条亮点（面试展开版）

### 亮点 1：用 LangGraph 把"对话"变成可控的状态机

**简历一句话**：意图识别与业务分支拆成图节点，取代"一个大 prompt 搞所有事"。

**怎么讲**：
- 单 prompt 方案三个致命问题：该追问时直接编答案、出错无法定位、加分支要改整段提示词
- 现在 `analyze` 只做分类和抽槽，`retrieve` 只管检索，`generate` 只管组织语言，`recommend` 只管推荐
- 条件边决定走向，界面能展示每一步轨迹——排查"为什么答偏了"时直接看是哪一步错了
- 意图判定优先用规则（关键词 + 长度），稳定、零 token、可解释；不用模型做分类是为了省成本、避免抖动

**可能被追问**：规则覆盖不全怎么办？
→ 规则兜底到 knowledge（最安全的默认），同时预留了 LLM 分类接口。真实业务里可以加一层小模型分类器，成本比大模型低两个数量级。

### 亮点 2：RAG 不只是"切块 + 塞 prompt"，检索要自己调出来

**简历一句话**：按业务结构两级切分，再用「召回 + IDF 加权重排」把检索准确率从"全部兜底"调到 top1 命中。

**怎么讲**（这段有真实踩坑，面试官很吃这套）：
- 一级按 `##` 标题切（养护知识天然按"症状/原因/处理"组织），二级用递归字符切分兜底
- 标题拼进向量文本：用户问"疫苗"，标题命中也算召回
- `<20 字` 碎片丢弃，避免无信息 chunk 占坑
- **第一版直接卡余弦阈值 0.18，结果 5 个测试问题全部走兜底**——所有片段分数都挤在 0.06-0.14
- 打印分数构成后定位到两个问题：余弦对文档长度敏感；中文 2-gram 把词边界切碎（"克猫粮"对不上"克干粮"）
- 改成 **`0.65×IDF 加权词项覆盖率 + 0.35×余弦`**，并让品种词（狗/猫）只做过滤不参与打分
- 修复后："狗狗拉稀"top1 从《呕吐》变成《腹泻与软便》，分数 0.128 → 0.383，top2 只有 0.154，区分度明显
- 阈值随之从 0.18 下调到 0.12（因为分数标尺变了），低于阈值直接说"知识库未覆盖"

**可能被追问**：怎么知道是检索问题还是生成问题？
→ 看执行轨迹。轨迹里会打「召回 N 条 / M 条达阈值 / 最高匹配度 X（覆盖率 A / 余弦 B）」。若最高分低 → 检索问题；若分数高但答案跑偏 → 生成问题（改 prompt）。**先用数据定位，再动手调**，这是我觉得比"堆功能"更有价值的一点。

### 亮点 3：双模式降级 —— 保证"任何人拿到都能跑"

**简历一句话**：模型和向量化都做了本地兜底，无 API Key 也能完整演示全流程。

**怎么讲**：
- 大模型：`auto` 模式自动探测 Key，没有则走模板；调用异常时 `generate` 返回 None，上层降级为抽取式摘要
- 向量化：默认用字符 n-gram 哈希（零下载），可选切到 `text-embedding-v3`
- 切换 embedding 后维度变了，`ensure_knowledge_base` 会自动检测并重建，不会静默出错

**为什么重要**：很多学生项目的 README 写着"填入你的 Key 后运行"，评委/面试官拿到手第一步就卡住。这个项目的取舍是"先能跑，再谈效果"。

**可能被追问**：离线模式算不算 AI？
→ 算 RAG 的检索部分 + 抽取式摘要，不是生成式。我把它定位为**可用性保障**，而不是效果上限；配上 Key 后是同一条链路换成生成式，接口没变。

### 亮点 4：把咨询变成订单（业务闭环）

**简历一句话**：推荐结果与业务系统同源，点一下就能下单。

**怎么讲**：
- `services.json` 的 id 与平台 `t_service.id` 一一对应，推荐卡片直跳 `/user/service/{id}`
- 平台下架的服务（`status=0`）自动过滤，不会推一个点进去发现已下架的服务
- 品种过滤：猫的服务不推给狗
- 打分融合：语义 0.5 + 规则 0.5，纯向量会推错品类，纯规则听不懂口语

**这是与传统"知识问答 Demo"最大的区别**：Agent 不止回答问题，还要往业务目标上走一步。

### 亮点 5：可调试性做进产品里

**简历一句话**：把 RAG 的黑盒变成可观察的白盒。

**怎么讲**：
- 界面可展开「参考资料」（含相似度分数）、「工作流轨迹」、「当前画像」
- 侧边栏能实时调 `top_k`、相似度阈值、推荐数量、温度
- 演示时把阈值从 0.12 调到 0.4，同一问题立刻变成"知识库未覆盖"——**看得见参数的作用**

## 三、60 秒项目介绍

> 这是一个宠物养护垂直领域的 RAG 智能体，和我做的宠物上门服务平台是打通的：用户问养护或症状问题，Agent 给出有依据的回答，如果判断需要人手上门，直接推荐平台里的服务并跳转预约。
>
> 技术上用 LangChain 做知识库和模型封装，用 LangGraph 编排对话流程——意图识别、槽位追问、检索、生成、推荐是独立节点，靠条件边路由，而不是一个大 prompt 硬塞。检索用的是 Chroma，文档按标题两级切分，加了相似度阈值兜底，检索不到就说不知道。
>
> 工程上做了个取舍：没有 API Key 也能完整跑，自动降级成抽取式摘要，这样任何人拿到代码都能立刻演示；配上通义或豆包的 Key 就切换成生成式，走的是 OpenAI 兼容协议，一套客户端能切两家。

## 四、高频追问与答法

**Q1：为什么不用 LangChain 的 AgentExecutor / ReAct？**
对话流程是**确定的业务分支**（问症状 / 问服务 / 闲聊），不是开放式工具调用。ReAct 让模型自己决定下一步，在这个场景里既慢又容易跑偏，还难调试。LangGraph 的图是显式声明的，路径可预期、可测试。

**Q2：召回不准怎么排查？**
四步：① 看轨迹里的最高相似度，判断是检索还是生成的问题；② 展开参考资料看 chunk 内容是否切碎；③ 调 `top_k` 看是否召回但排序靠后；④ 降阈值看是否被过滤。定位后再决定是改知识库、改切分、还是改阈值。

**Q3：怎么防止模型胡说？**
四道闸：prompt 里明确"只依据资料、不编药名剂量、不确定就说不知道"；检索相似度不足不进模型；模型异常降级模板；回答可展开引用供核对。另外用药剂量一律不给具体数字。

**Q4：chunk_size 怎么定的？**
先按 `##` 标题切，保证章节语义完整；章节过长再用 380 字 / 重叠 60 兜底。380 是权衡：太短会丢主语（"禁食 4-6 小时"不知道针对谁），太长会稀释 prompt。这个值可以在文档里改，也可以调 `config.py`。

**Q5：为什么默认本地 embedding？效果够吗？**
首要原因是可复现——默认模型要下载 80MB，国内新手第一步就失败。本地哈希向量对"关键词高度重合"的垂直问答够用，代价是没有语义泛化（"拉稀"≠"腹泻"），所以知识库内容里两种说法都写。要更强语义就切 `dashscope`，代码已支持自动重建。

**Q6：多轮里用户说"它"，你怎么知道指谁？**
当前靠画像兜：`analyze` 每轮把品种/年龄/症状 merge 进 `profile`，指代不明时用画像补全，并让模型结合近期 4 条对话。真正的解法是加一步指代消解（用 LLM 把"它吐了"改写成"布偶猫吐了"再检索），这是我列在演进里的下一步。

**Q7：怎么评估效果？**
目前是 badcase 驱动：把答得不好的问题记下来，改知识库或 prompt 后回归。规范化做法是建 30-50 条「问题-标准答案-应命中文档」的评估集，算 Recall@k 和 answer faithfulness（可参考 RAGAS）。这是我认为下一步最该补的工程能力。

**Q8：token 成本怎么控？**
意图识别走规则不花 token；history 只带最近 4 条；服务向量启动时预计算；知识库 embedding 只在构建时算一次。单轮问答的输入大约 800-1200 token。

**Q9：如果要做成产品，下一步做什么？**
① 换 FastAPI 提供接口，前端独立；② 记忆换 Redis checkpointer 支持多实例；③ 加检索 rerank 与 query 改写；④ 加 👍/👎 反馈闭环做 badcase 挖掘；⑤ 建评估集做 CI 回归。这些都是"从能演示到能上线"的必经步骤。

**Q10：这个项目最难的地方？**
是"让它在没有 Key 的机器上也能跑"。一开始只考虑接大模型，本地跑不起来就等于没交付。后来把 LLM 和 Embedding 都做成可降级的双实现，才真正满足"任何人 clone 下来就能演示"。这个取舍让我理解了工程上"可用性优先于效果上限"。

## 五、演示时的注意事项

1. **先演示流畅路径**（养护问答 + 服务推荐），再演示参数调试，别一上来就调阈值
2. 第 4 个问题（信息不足触发追问）一定要演示，这是"设计过"的证据
3. 展开「参考资料」和「工作流轨迹」，让评委看到不是黑盒
4. 如果现场没网/没 Key，**主动说明**这是降级模式，并指出切 Key 的配置项在哪——比掩饰好
5. 别忘了提"服务 id 和平台一一对应"，把两个项目串成一个完整故事
